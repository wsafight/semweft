# Semweft 产品需求

> 本文：背景、定位、典型场景与竞品。 [返回文档索引](../semweft.md)

## 1. 背景与问题

Coding Agent 已经能读代码、改代码、跑测试，也能使用符号检索和语义上下文工具。但在大型仓库和多服务系统中，检索范围、语义证据是否过期、动态关系和仓库外依赖常常不明确。模型容易把局部检索结果当作全部影响范围，开发者也难以核查它依据了哪些事实。漏改、上下文浪费和审查成本需要通过实际任务评测量化。

传统静态分析和符号工具已经进入 Agent 工作流。例如 SciTools Understand 提供 CLI、Python API 和 MCP，Serena 基于语言服务器提供符号工具。Semweft 需要通过证据透明、增量一致性、预算上下文和跨服务契约映射证明价值。竞品资料与核查日期见本文第 4 节。

|问题|表现|后果|
|---|---|---|
|Agent 靠 grep 和抽样阅读找调用方|漏掉宏、trait 和 interface 动态分发、函数指针、反射调用|改动不完整，引入回归|
|上下文靠整文件塞入|大量无关代码进入上下文|Token 成本高，回答质量反而下降|
|影响范围靠模型推断|说不出“有没有遗漏”，每次回答还可能不同|评审者无法信任 Agent 的改动|
|跨服务依赖不可见|IDL 嵌套引用、下游类型透传、字段使用方不明|连锁发布、线上契约故障、旧字段不敢删|
|工具之间证据口径不一致|索引、检索、规则和运行时观测缺少统一快照及范围声明|Agent 和评审者难以复核结论|

**核心判断**：静态分析提供声明范围内可追溯的结构证据，LLM 结合需求推理；Semweft 逐项披露分析范围与已知缺口。所有功能共用[核心概念与证据模型](evidence-model.md)第 2.3 节的承诺边界。

**不使用 AI 的场景同样存在**：Agent 的每次查询都消耗按量计费的 Token，许多团队和个人不会在每次阅读或复核代码时启用 Agent，部分环境也不允许把代码交给模型。Semweft 自身不调用模型，同一份结构证据应能被开发者直接使用：理解项目结构、追踪调用关系、复核一次改动。

## 2. 产品定位

### 2.1 愿景

成为 Coding Agent 的“代码事实层”：在读、改、审代码时，提供可复核的结构关系、候选影响范围和明确的分析边界，并让 Agent 与开发者能够使用同一份证据。不接入 Agent 时，开发者也能直接用 CLI 与报告看懂项目结构、复核改动，且不产生任何 Token 费用。

### 2.2 目标用户

|用户|典型诉求|主要入口|
|---|---|---|
|Coding Agent（Claude Code、Codex、Cursor 等）|查询结构证据；修改前评估候选影响；修改后检查已定义的规则|MCP、CLI|
|不使用 AI 的开发者与评审者|不为每次查询支付 Token；直接看懂 crate、模块、入口与依赖，追踪调用关系，复核改动|CLI 文本/Markdown 输出与依赖图导出（v0.1）；静态 HTML 报告（v0.3）；CI 报告|
|代码评审者和审批人|核查改动依据、已检查范围和待确认项，再决定是否批准|CLI Markdown 报告；v0.3 起静态 HTML 报告与桌面审查台；PR 影响报告|
|业务开发者|接手陌生代码库；评估一个改动的风险|CLI 与依赖图导出；后续 HTML 报告、桌面审查台、IDE 插件|
|Tech Lead 和架构师|发现架构腐化、循环依赖、分层违规|桌面审查台、报告、CI 门禁|
|平台和基础架构团队|跨服务依赖、IDL 兼容性、发布顺序编排|CI、HTTP API、桌面审查台|
|质量和合规团队|可复现的度量、规则检查和审计报告|CI、报告导出|

**首版用户**：在 Rust 仓库中完成跨文件改动的 Coding Agent，以及不借助 Agent、直接用 CLI 上手仓库和复核改动的开发者。两类用户读取同一份证据，后者在 v0.1 有独立的验收任务（见[路线图](roadmap.md)第 1 节）。架构治理、平台发布和合规团队是后续用户，不作为 v0.1 的交付范围。

### 2.3 设计原则

1. **事实优先**：结论依据代码、构建信息、Git 历史或运行时数据；风险评分、自然语言定位和仓库地图摘要等推断必须标注为“推断”，并附依据

2. **证据透明**：关系分别标注来源、确定性、运行时观测和新鲜度；范围声明披露已知缺口与失效单元，输出字段说明分页和截断

3. **本地优先**：默认在本机运行，代码不离开机器，无需账号；L3 可能执行仓库构建脚本，首次运行前通过 CLI 由用户确认信任，MCP 不交互授权（见[质量目标与评测](quality.md)的安全要求）

4. **增量可见**：编辑后先提供新的语法事实；受影响的语义事实立即失效，语义刷新耗时和范围单独报告

5. **Agent 原生**：接口按 Agent 的工作流设计，输出结构化、可分页、可按 Token 预算裁剪

6. **同一证据、多种入口**：MCP、CLI 和后续桌面审查台经共享 daemon 读取证据。snapshot_id 固定输入，复核同一分析视图还需固定 semantic_epoch；桌面端在核心查询闭环验证后交付

7. **不依赖模型可用**：Semweft 自身不调用模型。核心事实、导航、影响报告和依赖图在不接入 Agent、不消耗 Token 时同样完整可用；面向人的文本、Markdown、图和 HTML 输出只是同一响应的渲染层，共用 schema_version、统计口径与缺口披露。后续可选的模型能力（如向量检索）不得成为这些功能的前提

### 2.4 非目标

- 不做代码生成 Agent，只为 Agent 提供事实和护栏

- 不做形式化验证

- 不做代码托管平台或全公司代码搜索门户

- 首个版本不提供 SaaS 托管服务

### 2.5 首版工作流

Agent 先定位目标符号，再查询引用、受限调用图和候选影响范围；Semweft 返回源码位置、推导依据、构建条件及已知缺口。Agent 按预算取得上下文，修改代码后运行编译器和测试。Semweft 刷新索引并生成新的影响证据，供开发者复核。v0.2 起追加限定规则核验；业务语义和无法解析的动态关系始终保留人工或测试验证。完整案例见本文 3.1。

**无 Agent 工作流**：开发者用 semweft map 和依赖图导出了解 crate、模块、入口与依赖方向，用 search、symbol、refs、calls 在终端追踪关系；自己修改代码后，用 semweft impact --diff WORKTREE --format markdown 得到候选影响、按类别汇总的缺口和未检查项，逐条回到源码复核。命令与输出约定见[接口规格](interfaces.md)第 2 节。

## 3. 典型使用场景

### 3.1 Agent 安全修改一个公共函数

**示例任务**：库存模块的 Stock::deduct 原来允许 qty=0，现在要求返回业务错误，函数签名不变。编译器可能不会发现调用方行为已受影响。以下是工作流示例，不是已完成的实验。

|步骤|操作与返回|Agent 或人的责任|
|---|---|---|
|固定基线|建立 base snapshot，记录源码、Cargo 配置、依赖与索引器版本|明确任务需求和纳入的仓库|
|查候选影响|impact_of 返回调用方、引用位置与证据路径；两个 dyn 调用点列为候选集合缺口|核对未解析点与仓库外消费者|
|取上下文|context_pack 在选定 tokenizer 的 20k Token 预算内返回定义、调用方签名和相关类型；省略项有位置和续查入口|阅读关键调用方，判断哪些零数量调用需要调整|
|修改与验证|Agent 修改行为和已发现使用点，并运行编译、相关测试与项目要求的完整检查|补充零数量、边界输入和调用方行为的测试证据|
|刷新证据|发布新 snapshot_id 与 syntax_epoch，受影响语义先为 pending，完成后原子发布新 semantic_epoch 视图|选择所需分析视图，核对新鲜度和缺口|
|限定核验|v0.2 起 verify_change 运行声明规则，返回 findings 与证据不足状态|处理发现，并补充业务应改点的测试证据|
|人工审查|v0.1 用 CLI 报告，v0.3 起用审查台查看 diff、规则、测试与缺口|批准绑定两侧 snapshot_id、epochs、diff 与报告哈希|

**验收重点**：能否更早找到需要阅读的使用点、让每个结论可回到源码，并在证据不足时准确说明边界。签名变化和语义变化分别评测，编译器仍作为必要基线和验证工具。

### 3.2 其他场景

|场景|使用方式|价值|
|---|---|---|
|审查 Agent 的改动|Agent 完成后，在桌面审查台（v0.3）查看按来源和确定性区分的影响链路与 verify 结果，逐项确认后批准，驳回意见回传 Agent|评审者能区分已检查、候选与未知范围；评审耗时以对照实验测量|
|接手陌生代码库|Agent 调用 repo_map；人用 semweft map 的文本输出与 Mermaid/DOT 依赖图，再按调用关系读取关键实现|以实际任务测量定位耗时，与 IDE 加 rg 基线对照|
|无 Agent 改动复核|开发者或评审者对一次改动运行 impact Markdown 报告，或在 v0.3 起生成静态 HTML 报告分享|零 Token 获得带证据和缺口的影响清单；复核正确率与耗时以对照实验测量|
|PR 评审|v0.2 起 CI 贴影响报告；风险评分（实验性，带推断标记）与推荐评审人随所有权适配增加；v0.3 起报告链接可在审查台打开|帮助评审者优先查看影响较大的改动，效果以对照实验验证|
|大规模重构|查声明范围内使用点，按模块分批，并核验已实现规则|减少漏改，并持续显示剩余缺口|
|IDL 字段下线|contract_impact 查已建模使用点，补充外部消费者和历史消息验证|提供下线证据与仍待验证的范围|
|多服务发布|后续按具体兼容策略构建阶段约束并展示条件建议|识别顺序约束和缺失的部署前提|
|架构治理|arch check 作为 CI 门禁，存量基线逐步清理|防止架构持续腐化|
|依赖升级|查询分析范围内的 API 使用点，声明动态访问与外部调用缺口|提供升级调查依据|
|CI 提速|测试候选建议，并与项目完整测试策略结合|验证节省时间与遗漏风险|
|故障排查|find_paths 返回预算内的路径，并披露未建模异步边与截断|缩小调查范围|

## 4. 竞品与差异化

**核查口径**：2026-10-30 核对的官方资料表明 Understand 已提供 MCP、CLI 和 Python API。下表其他产品的能力、速度与成本在锁定版本后对照验证。

|比较对象|比较重点|Semweft 需要证明的价值|
|---|---|---|
|SciTools Understand|已有静态分析、图、CLI/Python API 与 MCP|开源边界、统一证据与快照、预算上下文及跨服务映射的实际效果；MCP 本身不是差异|
|Sourcegraph、Augment Context Engine|代码检索、导航与 Agent 上下文|本地部署和厂商中立的成本，及相同任务效果下的证据与 Token 收益|
|CodeQL|查询、规则与代码分析|结构影响工作流的便利程度；查询速度需同数据和查询预算测量|
|Serena|语言服务器支持的符号工作流|持久证据、跨查询快照和影响闭环的收益；与成熟符号基线对比|
|Claude Code、Cursor 等 Agent 自带的 LSP 与代码索引|内置的定义跳转、引用和语义检索，用户无需额外安装|v0.1 首先要超过的基线：证据标注、跨查询快照和影响闭环能否在相同任务上带来可测收益，并抵消额外安装和索引成本|
|Aider repo map|结构地图与上下文选择|语义关系及预算选择带来的任务效果与 Token 收益|
|buf breaking 等 IDL 工具|按明确兼容模式检查 schema 变化|把兼容性发现连接到有映射证据的业务使用点，不替代协议规则工具|
|Glean、Kythe|代码事实索引与可扩展查询|小团队本地使用的安装与维护成本，不预设部署与性能结论|
|rg、文件读取与 Agent 现有工具|低成本且覆盖自由文本的检索|结构关系收益能否抵消安装、索引、工具输出和候选阅读成本；两者可互补|
|RustRover 等 IDE、cargo metadata、cargo-modules|人工导航、crate 与模块结构浏览|不使用 AI 时的主要基线：单纯结构浏览不构成差异；需证明证据标注、可复现快照、按类别汇总的缺口和影响报告能在上手与复核任务上提高正确率或缩短耗时|

**差异化必须可测**：同一次任务中，Agent 和人是否能复核相同快照的证据；候选与缺口能否正确提示；成功率不下降时 Token 和审查时间是否降低；契约映射能否定位独立标注的使用点。桌面界面只是承载这些证据的入口。

**官方参考**：能力引用按以上日期核查，实际集成前仍需固定版本。

- [Understand MCP 接入](https://docs.scitools.com/help/ai/connect-via-mcp.html)与 [Python API](https://docs.scitools.com/help/apis/python-getting-started.html)：已有 Agent 和脚本接口。

- [SCIP 协议](https://scip-code.org/index.html)：代码导航索引，不等于完整调用图。

- [MCP Resources（2025-11-25）](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)：资源订阅与更新通知为可选能力；客户端唤醒行为需验证。

- [SWE-bench Multilingual](https://www.swebench.com/multilingual.html)与 [Multi-SWE-bench](https://multi-swe-bench.github.io/)：具体样本与版本在实验开始前固定。
